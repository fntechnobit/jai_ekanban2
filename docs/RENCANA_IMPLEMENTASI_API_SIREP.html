Rencana Implementasi API SIREP1. Ringkasan

1. Ringkasan & Keputusan yang Dibutuhkan

Temuan utama — kabar baik Field shift memang tidak ada di API baru, dan itu tidak menjadi masalah. Hasil penelusuran kode: kedua aplikasi tidak pernah memakai shift dari listing untuk menentukan jadwal. Shift diturunkan dari master conveyor (shift_qty / int_shift_qty) saat alokasi kapasitas. Nilai shift hanya disalin ke staging lalu diabaikan. Ini menghapus satu-satunya calon penghambat besar.

Kesimpulan kesesuaian: dari 12 field yang benar-benar dikonsumsi kedua aplikasi, 9 field tersedia langsung, 2 field perlu aturan konversi (snp/plt yang di API terpecah menjadi versi sea dan air), dan 1 field (mode) perlu penegasan makna. Nama conveyor pada API (AT16, AT19, AB9) sudah cocok dengan master conveyor kedua aplikasi.

Yang menghambat dan harus dijawab tim PPC lebih dulu:

NoIsuDampak bila tidak diselesaikan
1 Tidak ada penanda perubahan (updated_at / revision) Revisi qty dari PPC tidak akan pernah sampai ke lantai produksi. Kedua aplikasi melewati baris yang sudah ada di staging, bukan memperbaruinya.
2 Tidak ada penanda pembatalan Baris yang dihapus di SIREP tetap hidup di staging, tetap dijadwalkan, tetap dicetak jadi kanban.
3 Parameter conveyor tunggal Sinkronisasi kami menarik semua conveyor sekaligus per rentang tanggal. Bila parameter wajib dan hanya menerima satu nilai, satu sinkronisasi menjadi puluhan panggilan HTTP.
4 Tidak ada paginasi & jumlah total Tidak ada cara memastikan data yang diterima lengkap. Rentang 31 hari × semua conveyor berpotensi ribuan baris dalam satu respons.
5 Aturan sea vs air snp dan plt tidak dapat diisi tanpa aturan pemilihan yang tegas.
6 Tanpa autentikasi, HTTP polos Data rencana produksi terbuka bagi siapa pun di jaringan yang sama.

Rencana Implementasi API SIREP4. Pertanyaan untuk Tim PPC

4. Daftar Pertanyaan untuk Tim PPC

Disusun menurut prioritas. Butir P1 menghambat penerapan; P2 dapat dikerjakan paralel; P3 penyempurnaan.

4.1 P1 Penanda perubahan data

Pertanyaan: apakah setiap baris listing dapat dilengkapi field updated_at (waktu perubahan terakhir) dan/atau revision (nomor revisi)?

Latar belakang: kedua aplikasi menyalin listing ke tabel staging lokal. Saat sinkronisasi ulang, baris yang kombinasinya sudah ada dilewati, bukan diperbarui — di ekanban lewat pemeriksaan exists(), di filter-kanban lewat INSERT IGNORE. Tanpa penanda perubahan, kami tidak punya cara membedakan “sudah ada dan sama” dari “sudah ada tetapi qty-nya berubah”.

Yang dibutuhkan minimal: field updated_at pada respons, ditambah parameter updated_since agar kami dapat menarik hanya yang berubah.

4.2 P1 Penanda pembatalan

Pertanyaan: apa yang terjadi bila tim PPC membatalkan atau menghapus satu baris listing — apakah baris itu hilang dari respons API?

Latar belakang: sinkronisasi kami hanya menambah dan melewati, tidak membandingkan isi staging dengan sumber untuk mencari baris yang hilang. Baris yang lenyap dari API akan tetap hidup di staging, tetap dijadwalkan, dan tetap dicetak menjadi kanban.

Yang dibutuhkan: baris yang dibatalkan tetap dikembalikan dengan penanda (mis. status: "cancelled" atau is_cancelled: true) beserta updated_at yang diperbarui.

4.3 P1 Parameter conveyor

Pertanyaan: apakah parameter conveyor wajib? Apakah dapat menerima beberapa nilai sekaligus (mis. conveyor=AT16,AT19) atau dikosongkan untuk mengambil semua?

Latar belakang: sinkronisasi kami berbasis rentang tanggal untuk seluruh conveyor sekaligus, dipanggil otomatis sebelum setiap proses penjadwalan. Bila satu panggilan hanya melayani satu conveyor, satu sinkronisasi berubah menjadi puluhan panggilan berurutan — lambat dan rawan gagal separuh jalan.

4.4 P1 Kestabilan id

Pertanyaan: apakah nilai id tetap sama sepanjang umur baris, termasuk setelah direvisi? Apakah id yang sudah terpakai bisa dipakai ulang untuk baris lain?

Latar belakang: id menjadi identitas sinkronisasi. Bila berubah saat revisi, satu baris demand akan tercatat dua kali di jadwal kami.

4.5 P2 Aturan sea vs air

Pertanyaan: untuk satu baris listing, mana yang berlaku — standard_packing_sea atau standard_packing_air? Apakah ditentukan oleh shipping_method?

Usulan kami (mohon dikonfirmasi):

snp  = shipping_method == "sea" ? standard_packing_sea : standard_packing_air
snpa = shipping_method == "sea" ? standard_packing_air : standard_packing_sea
plt  = shipping_method == "sea" ? max_pallet_sea       : max_pallet_air

Nilai snp menentukan jumlah box per kanban, jadi kesalahan aturan di sini langsung mengubah jumlah kanban yang tercetak.

4.6 P2 Arti mode

Pertanyaan: pada SIREP lama terdapat kolom mode bertipe angka (contoh nilai 1). Apakah shipping_method di API baru adalah pengganti kolom tersebut? Bila ya, mohon berikan tabel konversinya (mis. sea → 1, air → 2).

4.7 P2 Paginasi & jumlah total

Pertanyaan: berapa batas jumlah baris yang dikembalikan dalam satu respons? Apakah tersedia paginasi?

Yang dibutuhkan: amplop respons berisi jumlah total, mis. { "meta": { "total": 1243 }, "data": [ ... ] }. Tanpa itu kami tidak bisa memastikan data yang diterima lengkap — dan data yang terpotong senyap adalah kegagalan yang paling sulit dideteksi karena tidak menimbulkan error apa pun.

4.8 P2 Keamanan akses

Pertanyaan: apakah API akan tetap terbuka tanpa autentikasi?

Usulan: token sederhana per aplikasi konsumen melalui header Authorization, sehingga akses dapat dicabut atau dirotasi bila diperlukan. Bila HTTPS belum memungkinkan, minimal batasi akses berdasarkan alamat IP server e-Kanban dan Filter-Kanban.

4.9 P2 Arti is_printing dan is_printing_kanban

Pertanyaan: apakah kedua field ini diisi oleh SIREP sendiri, atau SIREP menunggu aplikasi kanban memperbaruinya setelah kanban dicetak?

Bila yang kedua, dibutuhkan endpoint tulis (mis. POST /api/shared/listing/{id}/printed). Ini justru peluang bagus — PPC akhirnya bisa melihat realisasi cetak di lantai produksi.

4.10 P2 Arti is_overtime dan status_assy

Pertanyaan: apakah is_overtime berarti baris tersebut dikerjakan pada jam lembur / shift tambahan? Bila ya, apakah kapasitas conveyor pada hari itu berbeda?

Perhitungan pembagian cutoff CO1–CO5 kami memakai kapasitas tetap per conveyor. Bila SIREP memiliki informasi kapasitas atau hari kerja per tanggal, itu sangat berguna dan sebaiknya disediakan sebagai endpoint terpisah.

4.11 P3 Keseragaman bentuk respons

Endpoint listing mengembalikan array telanjang, conveyor memakai amplop data. Mohon diseragamkan — kami mengusulkan keduanya memakai amplop { "meta": {...}, "data": [...] }.

4.12 P3 Daftar conveyor yang sudah pindah

Mohon daftar conveyor yang datanya sudah dikelola SIREP baru, beserta tanggal mulai berlakunya. Ini menentukan urutan peralihan di sisi kami (lihat §7).

5. Arsitektur Target — Dua Sumber Berdampingan

Karena sebagian conveyor masih dilayani SIREP lama, sumber data ditentukan per conveyor, bukan per aplikasi. Keduanya bermuara ke tabel staging yang sama sehingga seluruh logika penjadwalan di hilir tidak berubah sama sekali.

                    ┌────────────────────────┐
   SIREP lama ─────>│ DbListingSource        │──┐
   (DB langsung)    │ (koneksi mysql/listing)│  │
                    └────────────────────────┘  │   ┌──────────────────┐
                                                ├──>│ Normalisasi ke   │──> listing_stage
                    ┌────────────────────────┐  │   │ bentuk seragam   │    (tidak berubah)
   SIREP baru ─────>│ ApiListingSource       │──┘   └──────────────────┘         │
   (REST API)       │ (HTTP + adapter field) │                                   ▼
                    └────────────────────────┘                            assy_schedule
                              ▲                                                  │
                              │                                                  ▼
              master_conveyor.listing_source = 'db' | 'api'                    kanban
                    (penentu per conveyor)

5.1 Prinsip

PrinsipPenjelasan
Staging tidak diubahStruktur listing_stage / t_listing_stage tetap. Logika generate, verifikasi, dan kanban tidak tersentuh — risiko regresi ditekan seminimal mungkin.
Sumber ditentukan dataPerpindahan satu conveyor cukup mengubah satu nilai kolom, tanpa deploy ulang aplikasi.
Normalisasi di satu tempatKonversi sea/air, shipping_method, dan TRIM nama conveyor terjadi di satu kelas adapter — mudah diuji dan diperbaiki.
Kegagalan harus terlihatConveyor yang gagal ditarik dilaporkan ke layar, bukan hanya ke log. Ini memperbaiki kelemahan lama yang membuat rencana hilang diam-diam.
Bisa dikembalikan seketikaUbah listing_source kembali ke db → conveyor itu kembali memakai jalur lama.
Catatan penting — nomor id dari dua sumber SIREP lama dan SIREP baru memiliki penomoran id yang terpisah (contoh: 884213 di sistem lama, 250 di sistem baru). Selama masa dua sumber, id_listing tidak lagi unik secara global.
Hasil pemeriksaan: hal ini aman karena seluruh kunci yang dipakai kedua aplikasi selalu menyertakan conveyor dan tanggal — deduplikasi memakai (tanggal, conveyor, assycode, seq), dan relasi jadwal memakai id lokal tabel staging, bukan id_listing. Urutan FIFO juga hanya berlaku dalam satu grup (tanggal × conveyor).
Meski begitu, kolom penanda sumber tetap ditambahkan ke staging untuk penelusuran.

8. Tahapan Penerapan

TahapKegiatanKriteria selesai
0 Klarifikasi ke tim PPC Butir P1 (§4.1–4.4) terjawab. Daftar conveyor yang sudah pindah diterima. Uji panggil API dari server e-Kanban dan Filter-Kanban berhasil.
1 Penyelarasan master Seluruh nama conveyor dari /conveyor ada di master kedua aplikasi (setelah TRIM). Seluruh assy_number dari contoh data ada di master assy. Selisih dicatat dan diperbaiki.
2 Bangun lapisan sumber data Kode selesai. Dengan listing_source = 'db' untuk semua conveyor, perilaku identik dengan sekarang — tidak ada regresi.
3 Uji paralel satu conveyor Pilih satu conveyor percontohan (usulan: AT19, sudah dipastikan ada di kedua sisi). Tarik data dari dua sumber untuk rentang yang sama, bandingkan baris demi baris. Selisih nol.
4 Peralihan conveyor percontohan Ubah listing_source menjadi api. Pantau 5 hari kerja: jadwal terbentuk normal, kanban tercetak sesuai, tidak ada selisih qty.
5 Peralihan bertahap Pindahkan sisa conveyor maksimal 2–3 per minggu, urut menurut daftar dari PPC. Setiap gelombang diverifikasi sebelum lanjut.
6 Penanganan revisi & pembatalan Setelah jawaban P1 tersedia dan API diperbarui: aktifkan sinkronisasi delta dan pembaruan baris. Diuji dengan mengubah qty dan membatalkan baris di SIREP.
7 Pembersihan Setelah seluruh conveyor berjalur API dan stabil minimal satu bulan, koneksi database SIREP lama dinonaktifkan.
Urutan pemilihan conveyor Dahulukan conveyor dengan volume rendah dan variasi assy sedikit — dampak bila ada masalah lebih kecil dan penelusurannya lebih mudah. Conveyor dengan jadwal 2 shift dan volume tinggi sebaiknya dipindahkan pada gelombang terakhir.

9.2 Yang harus dipantau setelah peralihan

  • Jumlah baris staging per conveyor per hari — penurunan mendadak berarti ada yang gagal ditarik.
  • Daftar conveyor yang gagal dicocokkan ke master (kini ditampilkan ke layar, tidak lagi hanya di log).
  • Selisih antara qty listing dan qty kanban.
  • Waktu respons API — sinkronisasi berjalan sebelum tiap generate, jadi langsung terasa operator.

9.3 Rencana pengembalian

SituasiTindakan
Satu conveyor bermasalahUbah listing_source conveyor itu kembali ke db. Conveyor lain tidak terpengaruh.
API mati saat jam produksiSinkronisasi gagal dengan pesan jelas; penjadwalan tetap dapat berjalan dari data staging yang sudah tersimpan.
Data sudah telanjur salah dan terjadwalKembalikan sumber ke db, hapus staging rentang tersebut (baris terkunci tetap terlindungi), lalu generate ulang.
Kanban sudah telanjur tercetak salahProses unverify di aplikasi kanban — saldo carry-over dikembalikan — lalu ulangi dari staging.
Mengapa pengembalian murah Tidak ada perubahan struktur pada tabel staging maupun jadwal, dan tidak ada migrasi data yang perlu dibatalkan. Yang berubah hanya dari mana data diambil. Karena itu pengembalian cukup dengan mengubah satu nilai kolom pada master conveyor.

10. Daftar Risiko

RisikoDampakPenanganan
Revisi qty tidak terdeteksiTinggi Blokir peralihan penuh sampai P1 terjawab. Sementara itu, batasi peralihan pada conveyor yang rencananya jarang direvisi, dan sepakati agar revisi disampaikan manual ke operator kanban.
Pembatalan tidak terdeteksiTinggi Sama seperti di atas. Tambahan: sediakan tombol hapus staging manual per rentang bagi operator.
assy_number tidak cocok masterTinggi Diperiksa di Tahap 1 sebelum peralihan. Tambahkan peringatan di layar saat verifikasi bila ada assy tanpa pemetaan.
Nama conveyor tidak cocok / berspasiTinggi TRIM di kedua sisi + kolom sirep_conveyor_code untuk kasus nama berbeda. Conveyor gagal dilaporkan ke layar.
Aturan sea/air salahSedang Terdeteksi di uji paralel §9.1 — snp yang salah langsung mengubah jumlah kanban.
Respons terpotong tanpa errorSedang Minta meta.total (P2). Sementara itu, bandingkan jumlah baris terhadap hari sebelumnya dan beri peringatan bila turun drastis.
API lambat / tidak tersediaSedang Timeout + retry bertingkat. Staging lokal membuat produksi tetap berjalan.
Akses tanpa autentikasiSedang Usulkan token (P2). Minimal batasi berdasarkan alamat IP.
